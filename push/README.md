# Crush.X message popups — production integration pack (not yet installed in APK)

This branch provides a **server-side push outbox** and a **native Android data-only FCM handler**; it is not an already deployed integration. The GitHub checkout used here does not contain `frontend/android/app`, so the Java files are kept under `push/android/` for safe placement in the latest Windows Android project. **Do not replace existing MainActivity, AndroidManifest, or any Firebase service.**

## Server integration (private AWS service or worker)

1. On verified account login, register a random per-installation ID and FCM token through a *session-authenticated* HTTPS endpoint. Derive `authenticatedUserId` from Cognito JWT server-side; never accept it from the client's JSON body. Store installation ownership, token, platform, expiry and last-seen in a secure durable table. On logout/account switch, revoke backend ownership, clear Android account and notifications, and reconcile on reconnect. Never put Firebase service keys in the Android app or frontend.
2. After a real DM has been persisted to the canonical message database, enqueue its unique `eventId`. Instantiate `createMessagePush(...)` with durable adapters: `messageStore.getCommittedEvent`, `messageStore.canReceive`, `deviceStore.upsert/revoke/listActiveForUser`, `preferences.getForRecipient`, `outbox.tryClaim/markSent/release`, and `messenger.send` (e.g. Firebase Admin SDK on the backend). `outbox.tryClaim` must use atomic unique `(eventId,installationId)` and a bounded lease for worker-crash recovery; retry transient errors with backoff. Make SDK adapters match the installed Firebase version.
3. Send **data-only** payloads `{kind,eventId,conversationId,recipientId}` with high Android priority. Message text, sender names, avatars, access tokens and secrets are deliberately NOT included. All fields are string typed; the Android host renders generic text and the authenticated app fetches full content after tap. No fake delivered-message indicators.
4. Authorize each event to its recipient and check thread membership, blocked users, mute settings, deletion/retraction and account state **when sending**. Rate-limit and audit device registration and delivery attempts. Do not use user input directly as a push event.

## Android integration (actual Capacitor/Gradle source required)

1. Add `google-services.json` for the **correct Firebase project and `com.crushx.app` application ID** through the local Android build configuration; do not commit server credentials. Configure a compatible Google Services Gradle plugin and `com.google.firebase:firebase-messaging` SDK using the Android Firebase BoM. Confirm there is only one `FirebaseMessagingService` registered; **if Capacitor PushNotifications already owns FCM, integrate equivalent logic into that plugin instead of registering this class**.
2. Copy the three `push/android/*.java` files into `frontend/android/app/src/main/java/in/crushx/notifications/`; merge `push/android/AndroidManifest.merge.xml` entries into the existing manifest. Use the app's real launcher Activity; this code uses `getLaunchIntentForPackage()` and needs no hard-coded Activity class.
3. From authenticated host on login, call `PushAccountState.setActiveUser(context, verifiedUserId)`. On logout call `clearActiveUser`; revoke device token server-side. Retrieve `FirebaseMessaging.getInstance().getToken()` and `PushAccountState.latestToken()` from the native host on login/resume; register tokens through the authenticated API. On token rotation, `onNewToken` stores the latest token for sync. Ensure stable installation ID per app installation and rotate/revoke on account change. Avoid sending token from `FirebaseMessagingService` without a verified session.
4. Host Activity `onResume` calls `PushForegroundState.setVisible(true)` and `onPause` calls `setVisible(false)` so foreground WebSocket banners and system notifications do not duplicate. Request `POST_NOTIFICATIONS` runtime permission on Android 13+ with a contextual explanation; the user may decline. Create the high-importance channel on foreground startup if necessary. Android/user notification settings always override heads-up behavior.
5. In Activity `onCreate` AND `onNewIntent`, inspect `EXTRA_MESSAGE_ID`, `EXTRA_CONVERSATION_ID`, `EXTRA_RECIPIENT_ID`, preserve if the user needs to unlock, then verify the current authenticated account equals recipient and GET the real authorized notification/message from the backend. Only then open the full-screen conversation using your existing router. Never trust intent extras alone to access a conversation. Clear the consumed intent to avoid rerouting after activity rotation. If access is revoked, open Inbox, not private content.
6. The existing `heads-up-notifications.js` listens to `crushx:incoming-message`. Emit this event only from a trusted, authenticated, deduplicated WebSocket adapter for the active account. Use `crushx:conversation-opened` on navigation. Respect DND, silent threads, previews, muting and account changes.

## Test gates

- `node tests/message-push.cjs` verifies server registration, committed-message-only dispatch, mute/membership, de-dupe and private-data omission.
- `node tests/heads-up-notifications.cjs` covers in-app foreground popup behaviors.
- Build Android debug APK; test granted/denied permissions, foreground/background/killed process, launcher and cold notification tap, account switch, logout, muted chats, duplicate pushes, active chat, Reels/Story/Camera/Live overlays, dark mode, DND, battery restrictions and notification privacy on OnePlus 9 Pro API 34.
- No claim of end-to-end success until AWS DB, Cognito APIs, FCM configuration, APK and device tests are performed. Android `force stop` prevents normal push delivery until user relaunches.
